- AI risk assessment receives deterministic facts (Oslo date, daysUntil*, mission observers from personnel roles, missionFacts) computed in `ai-risk-assessment/missionContext.ts`; the AI must never infer dates, drones or crew from free text.
- Mission approval status is decided only by `decideApproval` in `ai-risk-assessment/approval.ts` (one source of truth for status, reason and severity); status is written only when the caller can update the mission or is assigned as personnel, and the result is persisted in `aiAnalysis.approvalDecision` so cards show the reason without new columns.
- Missing data is conservative, never fatal: `aiAnalysis.dataAvailability` flags population/airspace/weather; unavailable airspace caps the category (NO-GO kept when already NO-GO, otherwise BETINGET) with a "check manually" note, failed weather lookup leaves weather unassessed, and unknown population uses the highest band with no hard stop on missing values.
- The risk dialog resets assessment state per mission and guards responses by the selected mission (ref), so reopening with another mission never shows stale results; observer counts are set from the mission's personnel on each load, not merged with Math.max.
- iGRC, fGRC and SAIL are computed only in `_shared/soraGroundRisk.ts` (SORA 2.5 table, `applyGroundMitigations`, `lookupSail`); the AI only reproduces them, so numbers stay deterministic and fGRC > 7 never shows a SAIL.
- SORA re-assessment loads its base assessment from the DB by `previousAssessmentId` (caller RLS, newest base or a SORA row built on it, checked in `reassessTarget.ts`); client-sent analyses are ignored so results cannot be tampered with or built on stale data.
- AI risk assessment: all system decisions (hard stops incl. backup battery, iGRC/fGRC/SAIL, AEC/ARC, ALOS, equipment status, fog advisory) are built by `buildSystemDecisions` in `ai-risk-assessment/systemDecisions.ts` BEFORE the AI call and enforced after it via `consistency.ts`; the AI only writes prose and category scores, so it can never change a decision.
- Open vs specific is decided only by `classifyOperation` in `ai-risk-assessment/operationCategory.ts` (route.soraSettings.enabled is ignored); open-category assessments get containment 'Ikke relevant' while SORA reassessment always computes it, so adjacent-area warnings only appear where SORA applies.
- Confirmed SORA profiles (confirmed, current file, same company as the document) give default ground mitigations only inside their envelope and when each condition holds; evaluation lives only in `_shared/soraProfileEvaluation.ts`, drone coverage is decided solely by `aircraft[].droneIds`, priority is manual > profile > auto-M1C, and envelope deviations block auto-approval (status unchanged; only a manual submission sets pending_approval) but never cause a hard stop or NO-GO.
- Characteristic dimension/speed come from `resolveCharacteristics` in `_shared/soraGroundRisk.ts`: rows of a usable SORA profile linked via droneIds may only raise the catalog values (largest dimension incl. propellers), never lower them, and the iGRC text names the source.
- For specific-category operations, `stripOpenCategoryCompetency` (consistency.ts) removes recommendations demanding C-class/open-category competency, since competency is judged against the operational authorisation.
- The operation-category text (reasoning and category rules) is overwritten by `applyOperationCategoryText` (consistency.ts) from `classifyOperation(...).reasons`, so the AI never adds its own reasons or drone classes.
- Linked drone equipment/accessory notes are filtered by id via `linkedReasonsNotOnMission` (maintenanceStatus.ts): items also selected on the mission are judged only as mission equipment, never as "linked but not selected".
- SORA profile operation type is checked by rank (VLOS < EVLOS < BVLOS) against `flightInputs.isVlos`; a mission above the profile's type gives OPERATION_TYPE_EXCEEDED, which blocks profile reductions and auto-approval like the other blocking deviations.
- ALOS always uses the catalog body dimension (strictest); when iGRC uses a larger SORA-profile dimension, the ALOS text names both.
- Competency text: the AI receives only status/coveredBy/operatorApproval/recognised for specific or BVLOS operations (`buildCompetencyForAi`), and `applyCompetencyDecision` (consistency.ts) strips 'missing/lower competency' sentences and keeps the pilot score ≥ 7.0 when status is ok/assumed, so the AI cannot contradict the system's competency decision.
